# 3. Initial Audit of the Old Repository

A first-pass review found the following relevant issues:

### A. Missing package foundation

The supplied old project snapshot did not include a usable `package.json`, while the startup script expected `npm install` / `npm start`.

### B. Broken import paths

`src/bot.js` referenced paths such as:

```text
./services/stockService
```

while the actual `stockService.js` was outside `src/`.

### C. Missing services

The bot referenced services such as:

```text
ipoService
sentimentService
```

that were not present in the supplied project snapshot.

### D. Mock / simulated market data

`dashboard/api.js` explicitly contained a historical-data path described as:

```text
暫時返回模擬數據
```

Production RedwoodVest must contain zero mock market data paths.

### E. Scheduler inconsistency

A VIP report scheduler existed but was not wired into the main `startAll()` path.

### F. Database / async concerns

Some code attempted to `await` callback-style SQLite methods directly. These paths should be reviewed rather than copied.

### G. Useful parts worth preserving conceptually

The old project already contained useful concepts:

- Telegraf Telegram Bot structure
- SQLite
- scheduler
- Polygon
- Twelve Data
- Alpha Vantage
- Magnificent Seven report logic
- Telegram report formatting

Use them as reference only.

# 7. Redwood Signal Score

The official proprietary score is:

```text
Redwood Signal Score
```

The Score:

- is deterministic
- uses validated market/event inputs
- is not generated by AI
- is not a guaranteed-return probability
- is used to rank research / attention priority
- should eventually accumulate history
- must have score version and timestamp

The full formula, weights and feature vector are proprietary server-side logic.

Do not expose the complete formula through client payloads.

# 11. Anti-Copy / Product Moat Direction

Do not treat a hidden AI prompt as the moat.

RedwoodVest should protect and compound:

- ranking logic

- user Watchlists
- personalization
- provider orchestration
- historical outcome data
- distribution

- keep credentials server-side
- keep scoring formula server-side
- expose only necessary UI fields
- do not expose the full normalized dataset unnecessarily
- use authenticated endpoints
- preserve audit/report IDs
- support rate limits and anti-scraping controls
- maintain score versions and historical data
